# 歷史純邏輯 API

不讀資料庫、不取得定位、不查地址、不依賴 React／React Native。每次呼叫只傳**一隻狗或手機**的資料；呼叫端負責對象隔離與資料取得。

`index.js` 匯出：

| API | 用途 |
| --- | --- |
| `HISTORY_CONFIG`, `configFor(subject)` | 狗／手機分開的設計門檻 |
| `distanceMeters(a, b)` | 球面直線距離，公尺 |
| `normalizeHistoryRows(rows, source?)` | 資料庫欄位轉為共同格式，不修改原始列 |
| `historySourceStream(rows, {source, replayHolds})` | 先篩來源、封包去重、重算停住、GPS 去重；回傳 `packets`／`points` |
| `filterHistoryPoints(points, {subject, config})` | 實測點、精度與跳點過濾；狗高速點暫存／補回 |
| `replayHistoryHolds(packets, {since, ...holdOptions})` | 共用 `IndoorHold.applyHistoryHolds`，最多往前 24 小時；模型／seed 可透過 `holdOptions` 提供 |
| `historyMovement(points, {subject, config})` | `edges`、`vehicles`、`switches`、計入距離；輸入為過濾後點 |
| `historyVisits(points, options)` | 造訪起訖、圈內點、扣除缺口的時間；輸入為過濾後點 |
| `historyStops(points, options)` | 路線／整天中位數、明顯停留、追加狀態（手機 2026-10-14 起不比中位數：`stayRatio: null`，≥ `stayMs` 就是停留） |
| `historyIndoorNodes(points, options)` | 室內小房子節點；使用重算後封包，不用 GPS 去重結果判斷封包缺口 |
| `historyDeparture(points, options)` | 確認狀態、自動範圍與手動範圍；輸入完整當天過濾後點，可提供完整交通分類 |
| `historyTimeline(rows, options)` | 整合入口：共同資料流、範圍、地點列、交通／缺口列、編號、距離與追加狀態 |
| `countDistances(edges, config)` | 判定表「距離怎麼加」：和「上一個有算進去的點」比，超過兩筆誤差較大者（至少 5 m，缺誤差值當 10 m）才算。手機（2026-10-13）：上一個算進去的點是走路中（moving、誤差 ≤ 10 m、速度扣掉速度誤差仍 ≥ 0.5 m/s）、這一點也是 moving 且誤差 ≤ 10 m、而且這段至少走到速度加總的 0.75 時，從 2 m 起算；誤差超過 20 m 又沒有走路速度（沒有或超過 3 m/s）的「確認移動」點（室內 Wi-Fi／電梯定位），和其後同樣粗的點，在更準的一點或停住之前都不算、不移動起點；兩點都有同一次記錄的 `odometer_m`（原生每秒定位累積的路程）時，算進去的距離改用兩點的路程差，不少於直線、不多於直線 × 1.5 + 5 m 與速度預算；沒有這欄（舊資料、雲端、狗）照舊用直線。手機（2026-10-14）：從靜止出發、5 分內在 100 m 內又靜止、沒有一步落在精細走路點的「來回」收回（`driftTrip`，見下面「一整天在家是一個停留」） |
| `dogHistoryRow(row, source)`, `phoneHistoryRow(row)`（`HistoryRows.js`） | `dog_status`／`supabase_dog_status`／`myLocationTracker` 的列轉成共同格式：封包時間＝手機收到的時間（雲端用 `track_at`），定位時間＝項圈的 `gps_time` |
| `HistoryText.js` | 清單與摘要的文字（文案表 c120–c344、c1276）：時長、距離（`km` 總數；列與游標用 `utils/distanceText`）、膠囊、移動段、H8 |

時間一律為 UTC 毫秒；公尺為 `distanceM`，持續時間為 `durationMs`。`subject` 為 `dog` 或 `phone`；`source` 為 `all`、`local`（接受 `ble` 別名）或 `cloud`。

共同列使用 `{time, latitude, longitude, source, slave_id, packetTime, locationTime, accuracy}`；`time`／`packetTime` 是封包時間，`locationTime` 是 GPS 定位時間。省略時間欄位時以 `time` 作為既有資料相容備援；明確的 `null` 定位時間不會變成封包時間。原始資料庫欄位會保留，CSV 可讀 `packets` 的原始座標。

`historyTimeline` 的主要選項：

- `dayStart`, `dayEnd`：手機目前時區的一天 `[start, end)`。呼叫端提供 UTC 界線，因此夏令時間的 23／25 小時日也能正確裁切。
- `today`, `now`：是否為今天與現在時間。過去日期按事後規則重算；不使用函式內的系統時鐘。
- `manualRange: {start, end?}`：省略 `end` 代表跟著最新資料。`range` 可直接指定已選好的實測範圍。
- `following`：終點是否延伸；預設為今天且沒有固定手動終點。記錄關閉時傳 `false`。
- `state`：上次結果的 `state`，用於保留已標停留。`timezone` 是識別的一部分；來源、開始、固定結束、時區、既有資料或相關車段改變時會重新計算。
- `replayHolds`：可替換停住重播；預設狗使用既有 IndoorHold 純邏輯，手機不使用。`holdOptions` 可傳 `seed`、`config`、`classify`。

讀取完整當天資料，並為跨午夜提供前一天的必要實測／停住脈絡（停住最多 24 小時）；可提供隔天第一筆以辨識跨午夜（`continuesNextDay`）。不虛構 00:00 定位。`packets` 為篩選去重後原始列，`points` 為選定範圍的顯示／實測流；月曆使用共同來源的封包有無資料，清單與距離使用同一份整理結果，匯出保留原始座標。

`nodes` 是排序後完整清單；`locations` 只有地點列，`sections` 只有交通／缺口列。型別：`departure`、`stop`、`switch`、`indoor`、`movement`、`gap`、`end`。交通方式：`walking`、`moving`、`driving`、`ride`、`gap`。停留與切換點共用 `number`；室內節點不編號。切換點沒有上下車文字與停留時間。節點座標可供後續非同步查地址。

缺口列保留前後實測時間與座標，但 `distanceM`／`countedDistanceM` 都是零；車段保留實際 `distanceM`，`countedDistanceM` 為零。合併停留保留 `interruptionMs`，供清單／PNG／GPX 顯示「不含中斷 N 分」。跨日節點使用 `continuesPreviousDay`／`continuesNextDay`；終點 `label` 為「現在」、「最後」或「結束」。

## 分鐘一定有列（2026-10-13）

選取範圍內，清單（`timelinePresentation`）有長度的列首尾相接：沒有空洞、沒有重疊；每列分鐘加上「不含中斷」等於它的起訖時鐘跨度。取代 #115「合併的走路不計中間未觀測時間」。

- 合併的走路：分鐘＝起訖跨度，距離仍是各段之和。
- 手機的缺口列（`沒有資料`，或 `reason: 'uncertain'` 的「GPS 訊號弱」）帶 `sameSession: true` 時是同一次記錄裡的中斷：短於 `listGapMs`（`HistoryConfig`，30 分）就不列出，時間直接併入旁邊有長度的列——先找停留（停留、停在原處、帶停留的出發／終點），再找走路，再找其他移動；不加任何註記（`unlocatedMs` 只在資料上記下併入多少，不顯示）。兩邊只有出發／終點這種點時照列出。兩段走路之間只有這種中斷時合為一段走路。
- 停留裡面的中斷（`stop.gaps`）同理：時間軸在兩端定位屬於同一個 session 時標 `sameSession`；短於 `listGapMs` 的算進停留分鐘，`interruptionMs` 減掉，不再顯示「不含中斷」。30 分以上、換 session（`sessionChange`）、或沒有 session 可證明（舊資料、狗）的中斷照樣扣掉並顯示「不含中斷 N 分」。
- `sameSession`：「GPS 訊號弱」單步兩端都有定位，除非兩端 session 明確不同；沒有定位的缺口要兩端是同一個已知 session。帶 `sessionChange: true`（#135）的列一律自成一列。狗的缺口列都有原因（收不到 GPS／沒收到訊號），沒有這兩種列，也沒有 session，所以不受影響。
- 游標：`shownRowAt` 找出那一刻所屬的清單列；併入的中斷裡，游標不說「這段沒資料」，停留裡就說那個停留（`shownStayDurationMs`，和清單同一個分鐘），走路裡就說已走距離。
- 不到 `gapMs`、沒有任何列的幾秒時間，在走路旁邊時歸那段走路。
- 地圖、`model.sections`、`model.edges`、匯出的 gaps 都不變：地圖照畫中斷，GPX 照在中斷處分段。地圖停留的 TalkBack 也用 `shownStayDurationMs`；GPX 停留航點不含併入的缺口（`excludedMs` 照舊）（下面併入的粗精度靜止時間則算進停留，和 #116 的同地中斷合併一樣）。
- 手機精度超過 `stayAccuracyM`（25 m）但在 `accuracyM`（50 m）內、偵測為靜止的點，仍進 `phoneStationaryPresentationStops`：座標取該段第一個 25 m 內的點，沒有就取第一點，並標 `coarse`／`accuracyM`。`mergePhoneSamePlaceStays` 把貼著同地停留（距離 ≤ `radiusM` + 該段最差精度）的 `coarse` 段併入那個停留：保留編號與座標，只延長分鐘；不會因此把兩個編號停留合併。其餘 `coarse` 段是不編號停留。
- 距離、CSV 列與 GPX 軌跡點不變。`__tests__/PhoneMinuteAccounting.test.js` 用虛構資料檢查這個不變量。
- 2026-10-13 掃描補上（`closeHoles`，狗和手機同一規則）：任何沒有列的時間（被拿掉的 0 m 走路、沒成停留的靜止點、進入室內前最後一步、兩個中斷之間的幾筆）都歸旁邊的列：走路（不到 `gapMs`）→ 停留（停留、室內、帶停留的出發／終點）→ 其他移動（狗的「移動」、開車；不到 `gapMs`）。兩邊只有中斷或出發／終點／恢復記錄時：不到 1 分鐘歸旁邊的中斷（兩個同種中斷之間只隔這段就合成一列，例如換 session 之間 40 秒的幾筆、被 5 秒走路切開的「GPS 訊號弱」）；1 分鐘以上是一個不編號的停留（`presentationOnly: 'between-breaks'`），出發／終點旁邊時成為它們的停留，恢復記錄那一點就是這個停留的開始。兩邊都是時刻列（出發、恢復記錄、終點），旁邊沒有中斷時，不論多短都是這個停留（2026-10-15：今天的清單在記錄恢復後幾秒，恢復記錄和「現在」之間的秒數不屬於任何列）。
- 手機的旅行列不吸收靜止時間（`phoneStillTravel`，只看有速度／動作欄位的新資料；舊資料只看幾何，照舊）：開車段結尾連續 `stayMs` 以上、每一點都在第一點 `radiusM` + 精度內、沒有確認移動、沒有量到 `stillMps` 以上速度的時間（停車後坐在車上、手機留在車裡）是不編號停留，開車到停下那一刻為止（只限車段真的在那裡結束，範圍裁切出的紅燈不算）；旁邊沒有走路也沒有停留、1 分鐘以上、0 m、沒有確認移動、每點都在第一點 `stillPlaceM` 內的「走路」也是不編號停留。旁邊的切換點拿掉（停留本身就是分界），恢復記錄併成停留的開始。地圖的路線、距離、CSV、GPX 不變。
- 開車走走停停（2026-10-14，使用者決定，只限手機：`vehicleMergeMs` 等設定在 `HistoryConfig`）：市區的機車／汽車在紅燈間只衝 10–30 秒，塞車時以走路的速度慢慢前進，原本前者湊不到 `enterMs`（30 秒）不會成為開車，後者 30 秒就被當成下車，兩段之間紅燈的 3 分鐘就成了停留。`stepVehicles` 的 `scan.chain` 記住剛看到的開車證據：剛結束的車段，或「衝刺」（連續快速邊至少 `vehicleBurstMs` 10 秒；快速＝幾何速度達 `vehicleSpeed`，或幾何速度達 `backtrackSpeed` 且手機自己量到的速度達 `vehicleSpeed`，一筆抖動不會切斷一段衝刺）。最後一段證據後 `vehicleMergeMs`（10 分）內又有衝刺、中間走路（量到 `stillMps`–`vehicleFootMaxMps` 2 m/s、沒有停住的邊）加起來不到 `vehicleFootMs`（90 秒），或還沒離開那裡 `vehicleFootM`（30 m）：同一趟車。剛結束的車段接著開（那次下車是紅燈、塞車或一筆弱訊號），衝刺加起來達 `enterMs` 就是從第一段衝刺開始的車段。停室內、換 session 時鏈斷掉。兩段之間的停留一定短於 10 分鐘，就成了開車的一部分；10 分以上的停留、真的下車走路（90 秒以上）照舊。狗不變。`TodayRouteEngine` 用同一個掃描：鏈還在時 `vehiclesSettledAt` 為 false，之後的邊還可能變成開車。
- 慢車（2026-10-14，使用者回報：18 km/h 的車列成「走路 25 分・860 m」，下一段走路拿到「2.6 km」；只限手機）：快速邊要 `vehicleSpeed`（5 m/s，18 km/h），穩定 18 km/h 上下的車有一半的邊差一點，連不成 `enterMs`；畫面情境 `demo-slowcar` 每一筆又寫 3.8 km/h，量到的速度也救不起來。現在 `stepVehicles` 另有 `scan.cruise`（換新物件、不改舊的）：每條邊幾何速度達 `cruiseSpeed`（15 km/h，每公里 4 分）、兩端精度都在 `coarseConfirmedAccuracyM`（20 m）內、手機沒有停住，連續 `cruiseMs`（2 分）而且離第一筆的直線距離至少是路程的 `cruiseProgress`（一半），就是車段（`startVehicle`：和 `enterMs` 一樣往回接 `backtrackSpeed` 的邊、接上 `scan.chain`）。選 15 km/h、2 分鐘：快走 6–7 km/h、慢跑 8–12 km/h 遠低於它，14.4 km/h（每公里 4 分 10 秒）跑 10 分鐘仍是走路（`HistoryDepartureLogic` 的跑步速度測試），追狗衝刺 2 分鐘前就結束；腳踏車、慢車穩定 15–20 km/h。只看幾何、不要求量到的速度同意：2 分鐘、至少 500 m 的前進不是定位飄移（飄移在一點附近打轉，或是粗定位）。14 天真實記錄的走路列上，15 km/h 以上、精度 20 m 內最長只連續 18 秒，沒有一天改變。狗沒有 `cruiseMs`，不變。
- 停車後下車（2026-10-14）：車段裡先停住（`scan.parked`：停住且量到不到 `stillMps`）`stayMs` 以上、接著走路下車時，車段到停下那一刻為止（走路的第一條邊時 `scan.footParked` 記住那段停車），停車那段是一般造訪、有編號的停留。以前車段一直到開始走路，那段停車只被 `phoneStillTravel` 切成不編號的停留。不到 `stayMs` 的停頓照舊算在車段裡；`scan.chain` 從停下那一刻起算，所以 `vehicleMergeMs` 內又開走時照舊是同一趟車。
- 每一列的距離只來自它自己那一段（2026-10-14，`countEdge`）：速度預算撐不起的位移（`moved > limit`）照舊先不算、起點不動（067：定位飄走又回來不算；確認得晚的慢走等到確認再算），但等的時候手機在一個點的 `radiusM` 內待滿 `stayMs`（`state.since`：`{ at, time }`），那段位移就不算、從這裡重新算。以前停留裡量到的速度（畫面情境每一筆 3.8 km/h）慢慢加到撐得起整趟車的跳躍，在停留裡算進 1.6 km，`historyTimeline` 再把停留裡算到的距離給下一段走路。只在手機（`speedBudget`）；`TodayRouteEngine` 的檢查點一起帶著 `since`。
- 停留自己的距離（2026-10-15，使用者，#200，只限手機）：停留裡算到的移動放在那個停留（節點的 `countedDistanceM`），不交給之後的走路列；到達後、離開前 `edgeMoveMs`（1 分）內的移動算旁邊那段走路。同地合併、短暫外出（`excursion`）、兩個停留之間的幾秒（`step`、`phoneStepCarry`）的距離都進合併後的停留。合計 `wanderM`（100 m）以上、分布在 `wanderMinutes`（10）個以上不同分鐘的停留帶 `wandering: true`：清單／PNG「在附近走動 N 分・M m」（c1405）、TalkBack（c1406）、游標（c1407）、GPX（c1408／c1409）。真實資料四天只有 10/11 16:21–18:10 一個（210 m、16 分鐘）；其他停留自己的距離最多 76 m（10/12 21:12 的 9 分鐘停留）。狗不變。`__tests__/PhoneWanderingStay.test.js`；`test-support/TimelineClocks.listedMetres` 是各列（含停留）的距離加總。
- 已知限制：一直用走路速度爬行 90 秒以上的塞車，和下車走路分不出來，照舊是走路。同一趟車裡短於 `listGapMs` 的弱訊號，清單把前後兩段開車合成一列（`timelinePresentation`，和走路一樣）。
- 手機不比「一般」（2026-10-14，使用者決定）：`HistoryConfig.phone.stayRatio` 為 `null`，`historyStops` 不跑中位數重播（`replayVisitDecisions`），扣掉中斷後 ≥ `stayMs`（3 分）的造訪就是停留；範圍整個在一個造訪裡時和 `alwaysStayMs` 一樣是「還在原地」，不編號。狗照舊 ≥ 3 分且 ≥ 中位數 3 倍（至少 5 次造訪）。原因：開車走走停停修好後，被誤判成走路的紅燈不再是造訪，真實記錄的「一般」從 0.2–2.6 分升到 4–16 分，狗散步途中 4–17 分的停留失去編號。`typicalMs` 對手機是 `null`。

## 已知缺口：狗在車上沒有 GPS（H2c 坐車段借用手機路線）

## 記錄工作階段切換的同地中斷（手機）

`session_id` 是手機每次啟動記錄服務就換的新 UUID（App 更新、程序被殺、使用者關掉再開記錄）。PR #116 的清單規則只把**同一個工作階段**的同地中斷併進停留；換了工作階段的中斷照「沒有資料」顯示。原本正式的停留判斷（`samePlaceGap`）沒有看工作階段，結果短的這種中斷在清單是「沒有資料」，長的卻變成一段沒中斷的停留，默默把關掉記錄的時間算進去。

短期規則：**清單的規則為準——無法證明的時間不算停留。**

- `samePlaceGap(a, b, config)`：手機兩端都有工作階段而且不同時回傳 `false`（`recordingSessionChanged`）。所以 `historyVisits` 在這裡結束造訪（不管多短，只要超過 `gapMs`；連不到 3 分鐘的切換本來就不算中斷），`phoneGapContinuity` 也不會接起來。只有一端有工作階段（舊資料）時照舊；狗沒有工作階段，不受影響。
- 清單：兩段停留各自編號，中間是一列「沒有資料」，起訖剛好是前一段的最後一筆和後一段的第一筆。這種缺口列帶 `sessionChange: true`：它永遠自己一列，不能被併進旁邊的列（例如短缺口註記「含 N 分未定位」的折疊只適用同一工作階段）。
- 距離不變：`historyEdge` 用 `samePlaceGap(..., { acrossSessions: true })`，跨工作階段的同地中斷仍是 `bridged`（不算走路、不切斷距離計算、不影響開車判斷），所以清單、摘要、「今天 x km」（`TodayRouteEngine`）的距離都和修正前一樣。`historyTimeline` 會把不在停留裡的 `bridged` 邊顯示成缺口列。顯示位置（`phoneStayDisplayAnchors`）也只看地點，切開的兩段停留共用一個標記座標。
- 同一工作階段的同地中斷照 #116：併進停留、清單不出現「沒有資料」。
- 匯出：快照的 `gaps` 含這一列，`stays` 是兩段；GPX 本來就在工作階段切換處分段，CSV 是原始列。

`__tests__/PhoneSessionBreakStay.test.js` 鎖住：長／短的切換都是兩段停留＋「沒有資料」、同一工作階段仍是一段、距離不變、狗不受影響。

長期想法：讓原生端明確記下「記錄關閉」的區間（服務停止、使用者關掉、程序被殺後下次啟動補記），歷史只把真正關閉的時間當中斷；工作階段換了但服務其實沒停（例如 App 更新後立即重啟）的同地中斷，就能像同一工作階段一樣算進停留。

## 清單列的文字（2026-10-13）

- 距離：移動段（`sectionText`，畫面與 PNG 清單）和游標標籤（`cursorLabel`）用全 App 共用的 `distanceText`（`src/utils/distanceText.js`，狗卡片的 `formatDistance` 是同一個函式）：不到 100 m 為 5 m 一階（`0 m`、`45 m`），100 m–1 km 為 10 m 一階（`340 m`），1 km 起一位小數的 km（`1.4 km`）；每一階用四捨五入後的值判斷。摘要（`summaryText`／`movementSummary`／範圍摘要）、「今天 x km」與匯出的總距離仍用 `km()`；CSV／GPX 不變。
- 分鐘：移動段顯示的距離不是 `0 m`、顯示分鐘（`displayDurationMs ?? durationMs`）四捨五入為 0 時，時間寫「不到 1 分」（c1276）。只改文字；`durationMs`／`displayDurationMs` 不變。
- 出發（在室內就不要出發了）：室內節點正好從第一筆開始時，`historyTimeline` 本來就不加出發節點（#64）；`timelinePresentation` 另外在第一列是出發、1 分鐘內接著室內節點、中間只有沒計入距離的走路／移動或 `uncertain` 列時，拿掉出發和中間那幾列，清單從室內開始。模型的 `departure` 節點、地圖起點與 CSV／GPX 不變。`__tests__/HistoryRowText.test.js` 用虛構資料檢查這三條。
- 跨午夜的起點：清單第一列是 `continuesPreviousDay` 的停留或室內、而且開始時刻在當地午夜後 3 分鐘（`gapMs`）內時，`timelinePresentation` 把那列的開始拉到 00:00，分鐘也從 00:00 算（「00:01 接續前一天」→「00:00 接續前一天」）；更晚才有第一筆就照第一筆。模型節點不變。
- 跨午夜的終點：`continuesNextDay` 的終點 `nodePill` 回傳 `null`（不寫「接續隔天」，c334 已移除）；範圍在停留裡結束時沒有終點列，最後一列就是那個停留「停 N 分」（2026-10-14）；`continuesNextDay` 的室內節點寫「室內・N 分」。節點欄位不變，`continuesNextDay` 仍保留給其他用途。

## 手機靜止時的粗定位（2026-10-13）

- 手機偵測器鎖定為靜止、精度超過 `stayAccuracyM`（25 m）但在 `accuracyM`（50 m）內的點，在造訪已有 25 m 內的靜止點、離造訪中心不超過 `stillPlaceM`、且之前沒有已判定的離開點時，算進該造訪的時間（不切開、不算中斷），但**不參與**代表位置的平均（只有 25 m 內的點投票；沒有其他點時才用全部）。只有粗定位、沒有 25 m 內靜止點的時段不在這裡變成停留。
- 偵測器判為 `unknown`、但自己量到的可信速度低於 `stillMps` 的點，不是走路：那段邊是 `uncertain`（「GPS 訊號弱」），不會變成 0 km 的走路分鐘。這種邊帶 `stillUnplaced`；同一次記錄裡連續這種邊、原始位置都在起點 `radiusM` + 該點精度內、達 `stayMs` 時，`phoneStationaryPresentationStops` 把它當成 `coarse` 的靜止段：貼著同地停留就併進那個停留，否則是不編號停留。所以清單「不到 30 分的中斷併入旁邊」不會把它併成 0 m 的走路。量到 ≥ `stillMps` 的可信速度仍照走路計算。
- `__tests__/PhoneCoarseStationary.test.js` 用虛構資料鎖住這些行為。

## 停留不再被切碎（手機，2026-10-13）

重播使用者的實機資料後確認的五個原因，各自修正（`__tests__/PhoneStayConsolidation.test.js` 用虛構資料鎖住）：

1. **沒有速度的飄移不是離開**：會記錄速度的手機列（有速度欄位、跑過動作偵測）中，完全沒有量到速度、也沒有偵測器確認移動的點（`quietFix`），在停留中心 `stillPlaceM`（100 m）內算在原地，和「量到靜止」一樣；`samePlaceGap` 的兩端也接受這種點（100 m 內）。量到的可信速度、確認移動、換 session（#135）都不算；舊資料沒有速度欄位，照舊只看幾何。2026-10-15（使用者，#200）：速度誤差太大的速度＝沒有速度（`measuredSpeedMps`：速度誤差超過 1.5 m/s、而且速度減掉誤差不到 0.5 m/s，例如室內的 0 km/h ± 2 m/s；和偵測器的 `phoneReliableSpeed` 同一條）。所以這種點也算在原地、可以當同地中斷的一端；減掉誤差仍超過 0.5 m/s 的（粗定位上的車速）照舊是速度。地圖的「中斷後在誤差內跳一下的到達線」（`stationaryRecoveryEdges`）在同地中斷之後也不畫。`__tests__/PhoneUncertainSpeed.test.js`。
2. **停留裡的飄移不變成走路**：停留裡算到的移動距離只在抵達後 `gapMs` 內才算進抵達那段步行，之後的（停了幾小時後的飄移、出發前的幾步）算進下一段步行，不會跨過缺口和其他停留算到幾小時前的步行。手機的同地中斷（`bridged`）之後從重新出現的位置繼續量距離，中斷兩端之間的飄移不算。停留旁邊 0 m、沒有確認移動、不到 `listGapMs`、每一點都在停留 `stillPlaceM` 內的走路併進那個停留（`foldPhoneStayWalks`）；兩個同地停留之間的這種走路讓兩個停留合為一個。旁邊沒有走路、只有停留時，列之間不到 `gapMs` 的空白（例如重新鎖定前的停頓）歸那個停留。
3. **午夜前後的空白也是一列**：`HistoryDatabase.historyDayRows`（手機）另外讀取讀取視窗前的最後一筆，以及視窗後的第一筆（找到之前每次輪詢都讀），不受 30 分／3 分限制。範圍從當天第一筆開始、前一筆早於它超過 `gapMs` 時加「沒有資料 00:00–第一筆」（`dayBoundary: 'start'`）；固定終點在當天最後一筆、隔天第一筆晚於它超過 `gapMs` 時，在終點列之後加「沒有資料 最後–24:00」（`dayBoundary: 'end'`，文字寫 24:00）。換 session 一律自成一列；同一 session 不到 30 分折進旁邊的停留列（#132）；同一 session 同地（`samePlaceGap`，停留跨過午夜）不論多長都是停留時間，兩天一致：旁邊有停留列就算進它，否則那一段本身就是停留——當天第一列是「接續前一天」（取代只有一點的出發），或那個停留就是最後一列「停 N 分」，一直到 24:00（`presentationOnly: 'carried-over'`，不編號；沒有終點列，2026-10-14）。和「跨午夜的起點」（#146）同一個結果：第一筆在午夜後 3 分鐘內時沒有這種列，由 `fromMidnight` 把「接續前一天」拉到 00:00；更晚時由這裡從 00:00 起算，分鐘都從 00:00 算。其他情況旁邊只有出發／終點這種點時照列出。另一邊沒有任何一筆、或今天還在跟著現在時不加。CSV、GPX 的資料列不變。
4. **「還在原地」的停留也在清單上**：`displayStays`（範圍整個落在已確認的長停留裡）另外成為不編號的清單節點（`presentationOnly: 'still-here'`），是清單唯一的一列（2026-10-14：沒有「出發」、也沒有終點列），「停 N 分」和地圖標籤、游標同一個分鐘。仍不編號、不是 GPX 停留航點。
5. **同地停留之間的短暫真的走路**：兩個停留之間的走路，從第一個停留結束到手機重新停下（`leaveMs` 沒有移動、在半徑內）不超過 `excursionMs`（5 分），而且這段期間最遠的點和第二個停留都在第一個停留的半徑內，半徑 = `excursionAccuracyFactor`（2）× 第一個停留的精度中位數，限制在 `excursionMinM`–`excursionMaxM`（30–50 m），不是 100 m：三者合為一個停留。這段走路的距離照樣算，歸抵達第一個停留的步行，沒有就歸下一段步行；兩者都沒有時不合併，清單加總仍等於摘要。否則照樣分開。

6. **慢走不是停留**（2026-10-14）：回放的列 5 秒一筆，`PhoneMotion` 的高精度幾何離開以前湊不到 19 秒的視窗，3–4 km/h、速度在誤差內的散步一直鎖在停留點（實機 4 段、約 69 分鐘的 0 m 停留）。偵測器的修正見 `src/locationTracker/README.md`；歷史這邊的 `stillPlaceM`、`quietFix`、同地合併、短暫走路合併規則都沒改：這些散步的點量得到速度，本來就不是 `quietFix`，被吃掉是因為偵測器沒有放開鎖定（`phoneStationary`）。

   - **整個範圍就是一個造訪時一定有一列**（`historyStops`）：以前它不編號（範圍就是它：還在原地），但只要範圍裡有確認移動或算到距離就不是「還在原地」，於是兩者都不是，只剩 PR 116 的備援在偵測器動搖的地方切成好幾段不編號的停留。現在：停留中心 `stillPlaceM` 內的確認移動不算離開，沒有算到距離、沒有開車時就是「還在原地」（一列、起點也是終點）；有算到距離（收回的來回不算）或開車、或確認移動超過 `stillPlaceM` 時，在那裡切開，兩邊各自是停留（範圍的第一列和最後一列），中間是那段移動。範圍裡沒有任何一段在造訪之外的走路時，每個造訪都這樣切開：停留裡算到的距離要有一列走路可以放。距離用範圍自己的邊（`rangeEdges`，從範圍第一筆重新算，和摘要一樣）。
   - **同地、只隔一下的停留是一個**（`mergePhoneSamePlaceStays`）：不編號的停留（`presentationOnly`）和前一個停留在同一地方（`radiusM` + 精度內）、中間只有不到 `gapMs` 沒有列的秒數、0 m 的走路或同一 session 的短暫弱訊號（GPS 跳一下、偵測器動搖）時合為一個；兩個編號停留之間只有這些、合起來不超過 `excursionMs` 時也合為一個（電梯被切開的造訪）。短於 `gapMs` 的換 session（App 安裝）一律併進停留：和 `historyVisits` 同一個門檻（只有超過 `gapMs` 的中斷才結束造訪），超過的照 #135 是自己一列「沒有資料」。兩個停留之間 1 分鐘以內的 0 m 走路先留著給合併和 `foldPhoneStayWalks` 判斷，沒用到再由 `emptyPhoneFootRows` 拿掉。

   - **摘要等於各列加總**：停留裡算到、等著下一段走路但之後沒有走路的距離，交給最後一段走路（10/13 的 4.519 km 對各列 4.459 km：22:09 的 60 m 是最後一個停留裡的一筆粗定位，現在是收回的來回）。「今天 x km」本來就是各邊的加總，所以三者相同。`__tests__/PhoneDayAtHome.test.js` 用虛構的桃園資料鎖住：在家一天（GPS 跳點、電梯、兩次 App 安裝）是一列、0 km、每個時刻加得起來；電梯收回、信箱來回照算；切開的造訪；短中斷合併、長中斷照列。

1、3、4、5 和 2 的折疊只套用在手機。2 的距離歸屬（抵達後 `gapMs`）是狗和手機共用的時間軸邏輯：狗的停留裡、抵達很久以後的移動，同樣改算進下一段「移動」，總距離不變。

## 不寫「出發」（2026-10-14，使用者決定）

範圍從移動開始時，第一列（`departure` 節點）照舊是起點的空心圓，但 `nodePill` 回傳 `null`：只有時間和地址，沒有膠囊，和終點一樣不寫字；TalkBack（`placeSpeech`）唸「地址，07:02」。匯出 PNG 的起點列相同；GPX 沒有起點航點（軌跡從那裡開始），地圖起點是空心的時間標記，都沒有字。c124「出發」退休（`I18nArchitecture` 檢查它不在資源裡）。程式、模型和註解裡的 `departure`／「出發偵測」照舊，只是畫面不再寫這兩個字；範圍條的「開始／結束時間」不變。

## 「今天 x km」和摘要是同一個數字（2026-10-15）

`TodayRouteEngine`（「今天 x km」）和 `historyTimeline`（歷史摘要）跑同一套規則，但以前讀的欄位不同：`HistoryDatabase.phoneRouteSince` 沒讀 `raw_latitude`／`raw_longitude`。`PhoneMotion` 用 `raw_latitude ?? latitude`，原生記錄器在手機靜止時把 `latitude`／`longitude` 釘在錨點上，所以藥丸的動作偵測看的是釘住的座標，歷史看的是原始定位，靜止／移動判斷不同，算到的距離也不同。在本機唯讀重播使用者真實的 14 天（每 10 分鐘一個檢查點，共 1,444 個），有 334 個檢查點不一致，最多差 100 m；藥丸和摘要有時差 0.1 km。

現在兩邊讀同一份欄位清單 `PHONE_MODEL_COLUMNS`（原始定位、速度、偵測器狀態、工作階段、里程）：`phoneRouteSince` 和 `historyDayRows`（手機）都從它選欄位，表格有的欄位每一列都有這個鍵（沒有值時為 `null`），和 `historyDayRows` 的列一樣。同樣的重播現在 0 個不一致。`__tests__/TodayRouteColumns.test.js` 用虛構、像原生那樣釘住座標的一天，經過真的 `phoneRouteSince` 和 `historyDayRows`，檢查每 10 分鐘藥丸都等於摘要。
