# 歷史地圖記憶體修正

2026-09-22 Samsung 調查發現，M5／M7 的相同 Slave 記錄交替，造成三小時約 1,533 條短 Polyline。回前景重建 MapView 後，舊 SDK 地圖仍被回呼引用，heap 可同時保留約 4,715 條 Polyline。

本次修正：

- 歷史線按 Master／Slave／手機 session 分流，再依有效定位、兩分鐘斷訊與換日線切段。不同 Master 不互相接線；CSV 保持所有記錄，GPX 亦按來源分段。
- 全部歷史軌跡共用 120 條原生線段、4,000 頂點上限，優先保留較新部分。圖上提示達到上限，SQLite 與完整匯出不受影響。
- 正常回前景沿用 MapView，保留相機與游標。底圖異常可按「重試地圖」手動重建。
- 短於十秒的背景切換不提前重新查詢歷史；離開頁面取消排程，排隊中已失效的讀取不再開始掃描。這是快取與查詢節流，尚不是 SQLite 全面的增量游標查詢；仍以每頁 1,000 筆讀取選定時間範圍。
- 手機即時藍點在原始速度 < 1 km/h 且有有效精度時，抑制半徑 min(3 m, accuracy / 3) 內的小漂移。距離相對保持的座標計算，累積離開範圍就更新；正常速度、未知速度、新 session、定位中斷及原本靜止鎖定各沿用既有規則。歷史重播不再做一次漂移抑制。

原始 GPS 與既有平滑欄位不重寫。藍點顯示位置仍經既有 displayPosition 流程另存，沒有改 SQLite 儲存頻率。這個小範圍顯示抑制無法消除所有窗邊多路徑誤差，也沒有改變雲端／BLE 的持久化平滑版本。

驗證包含交替 Master 大資料量、GPX 全量保留、全圖預算、時間到期、回前景 MapView 身分、查詢節流／帳號切換及低速漂移退出。仍需更新手機後重新量測 Java Heap，才能宣稱裝置上的 OOM 已排除。

使用調查時保存的手機 SQLite 副本重播 16:55 前三小時：Slave 4／6／8 分別 2,157／2,157／2,159 筆，修正後各兩條來源獨立線段，合計六條、208 個頂點，未觸及繪圖上限。原流程的同一範圍為 1,533 條可繪製短線。
